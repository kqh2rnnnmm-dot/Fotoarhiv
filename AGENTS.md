# AGENTS.md — инженерные правила «Фотоархива»

## Контекст
«Фотоархив» — локальный фотоорганайзер для Windows 10 x64 (основная ОС пользователя) и Windows 11 x64. Виртуальная фотобиблиотека агрегирует несколько папок/дисков без изменения оригиналов; последующие фазы добавят карту, похожие снимки и подтверждаемые операции сборки архива. Пользователь — не разработчик; интерфейс и итоговые инструкции на русском.

## Текущий проект
- Решение: `Fotoarhiv.slnx`.
- WPF: `src/Fotoarhiv.App` (net10.0-windows).
- Ядро: `src/Fotoarhiv.Core` (net10.0, SQLite, MetadataExtractor).
- Тесты: `tests/Fotoarhiv.Tests` (xUnit).
- CI: `.github/workflows/build-windows.yml`.
- Контрольная точка v0.2.1: Windows Actions run 41348272593 успешно выполнил Release build, 18 xUnit-тестов, self-contained publish, запуск/закрытие окна и 16 GUI-проверок на Windows Server 2025. Windows 11 на ПК пользователя и пять дополнительных GUI/физических сценариев ещё НЕ проверены; полный P0 остаётся открыт. Текущая задача: `tasks/CODEX_TASK_003_UI_PARITY_RU.md`: восстановление UI по авторитетному локальному HTML/PNG, с сохранением ядра; прежние доказательства — `BUILD_REPORT_RU.md`.
- Никогда не включать в поставку старую v0.1 с VBS, PowerShell или `.cmd` запуска.

## Жёсткие инварианты
1. При индексации исходные файлы и папки доступны лишь для чтения. Не изменять метаданные, даты, имена, расположение или содержимое. Хранить базу/кеш/логи только в отдельных папках приложения.
2. Не реализовывать удаление исходных снимков и массовое перемещение в P0. Физическая сборка — отдельный этап с dry run, явным подтверждением, отсутствием перезаписи без выбора, проверкой SHA-256 и устойчивым журналом операций.
3. Не считать визуальное сходство строгой идентичностью. Точный дубль = равное содержимое, подтверждённое SHA-256. Состояние записи и хеша должно инвалидироваться при изменении исходного файла.
4. EXIF-дата съёмки приоритетнее файловой даты; fallback явно помечать. Не придумывать время/координаты. Отсутствующие источники не очищать из каталога автоматически.
5. Не загружать фото/EXIF/GPS в сеть. Открытие карты в браузере — только по действию пользователя; отдельно учитывать возможную передачу GPS выбранной точки сервису карты.
6. При ошибке, отмене или отключении диска сохранять работоспособность приложения; не показывать ложный «успех».
7. Не пытаться обходить антивирус, ExecutionPolicy, SmartScreen. Не запускать приложение через VBS/PowerShell. Не обещать отсутствие предупреждений для неподписанного exe.

## Стиль и UX
Минимальные действия, понятные русские подписи, единая система отступов/типографики. Не редизайнить существующее приложение за пределами задачи. Приоритет: хронология, карта, повторы, источники, сборка архива. Критические операции всегда имеют предварительный просмотр и точное описание последствий.

## Порядок инженерной работы
- Перед изменением изучить относящиеся к задаче файлы, без ненужного переписывания проекта.
- Для нового поведения и исправления дефекта: сначала тест, демонстрирующий ожидаемое поведение/ошибку, затем реализация; запустить целевые и полные тесты.
- Компиляция и тесты должны запускаться на Windows runner/Windows-машине. Если доступа нет, указывать «не проверено», а не симулировать успех.
- Пример проверки в среде разработки: `dotnet restore Fotoarhiv.slnx`, `dotnet test Fotoarhiv.slnx -c Release`, `dotnet publish src/Fotoarhiv.App/Fotoarhiv.App.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:PublishTrimmed=false -o publish`.
- Релизный ZIP должен содержать рабочие файлы publish целиком, а не произвольно выбранный exe. Не предполагать, что один exe гарантированно достаточен.
- Тестировать хотя бы: два одинаковых файла с разными именами; два равных по размеру, но разных по содержимому; отсутствие EXIF; EXIF дата; GPS; отключённый диск; отмена сканирования; повторное сканирование и обновление хешей; запрет модификации оригиналов; ошибки доступа.
